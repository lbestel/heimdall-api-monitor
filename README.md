# Heimdall

> API monitoring system built with Python, focused on Object-Oriented Programming, Clean Code and software architecture.

Heimdall is an API monitoring system designed to check the health of HTTP endpoints and provide a clear classification of their current state.

The project is being developed with a focus on practicing software engineering principles such as **Object-Oriented Programming (OOP)**, **Clean Code**, separation of responsibilities and automated testing.

---

## 🚧 Current Status

**V1 — Monitoring Core**

The core monitoring engine is implemented and functional.

The current version can:

- Configure HTTP monitors;
- Send HTTP requests;
- Validate the returned HTTP status;
- Compare the response against the expected status;
- Measure request latency;
- Detect request timeouts;
- Classify the health of an endpoint;
- Return a structured `CheckResult`.

The system currently runs through the terminal using `main.py`.

## 🩺 Health Classification

Heimdall classifies an endpoint based on both the expected HTTP status and the actual response.

The current decision flow is:

```text
                         Response received?
                         /                \
                       NO                 YES
                       │                   │
                     DOWN            Expected status?
                                      /            \
                                    YES             NO
                                    │                │
                                   UP             Which status?
                                                 /          \
                                               4xx/5xx    2xx/3xx
                                                 │            │
                                               DOWN       DEGRADED
```
## Examples

If the expected status is 200:
| Expected | Received         | Health Status |
| -------- | ---------------- | ------------- |
| 200      | 200              | `UP`          |
| 200      | 201              | `DEGRADED`    |
| 200      | 202              | `DEGRADED`    |
| 200      | 204              | `DEGRADED`    |
| 200      | 301              | `DEGRADED`    |
| 200      | 302              | `DEGRADED`    |
| 200      | 400              | `DOWN`        |
| 200      | 404              | `DOWN`        |
| 200      | 500              | `DOWN`        |
| 200      | 503              | `DOWN`        |
| 200      | Timeout          | `DOWN`        |
| 200      | Connection Error | `DOWN`        |

This distinction allows Heimdall to differentiate between an endpoint that is completely unavailable and one that is responding but not behaving as expected.

## 🏗️ Architecture

The current core follows a simple flow:
```text
Monitor
   ↓
MonitorService
   ↓
HttpClient
   ↓
HTTP Response
   ↓
CheckResult
```
The project is organized into separate layers with different responsibilities:
```text
src/
├── application/
│   └── services/
│       └── monitor_service.py
│
├── domain/
│   ├── entities/
│   │   ├── monitor.py
│   │   └── checkresult.py
│   │
│   └── value_objects/
│       └── http_status.py
│
└── infrastructure/
    └── http/
        └── httpclient.py
```

## Domain
Contains the core concepts of the monitoring system.

- `Monitor` — represents an endpoint that should be monitored.
- `CheckResult` — represents the result of a monitoring check.
- `HttpStatus` — encapsulates HTTP status classification.

## Application
Contains the application logic responsible for executing a monitoring check.

- `MonitorService` — coordinates the HTTP request, status evaluation and result generation.

## Infrastructure

Contains external concerns.

`HttpClient` — responsible for making HTTP requests using `httpx`.

## 🧱 Core Model
A monitor contains the information required to perform a check:
```text
Monitor
├── monitor_id
├── name
├── url
├── method
├── expected_status
└── timeout
```

A check produces a `CheckResult`:
```text
CheckResult
├── monitor_id
├── health_status
├── expected_status
├── http_status
├── latency_ms
├── reason
└── checked_at
```
This separation keeps the configuration of a monitor independent from the result generated by its execution.

## ▶️ Running the Project
The current version runs directly through the terminal using `main.py`.
Run:
```bash
poetry run python main.py
```
The `main.py` file contains example monitors used to demonstrate different monitoring scenarios.

For example:
```python
google = Monitor(
    1,
    "Google",
    "https://www.google.com",
    "GET",
    200,
    5,
)
```
The result is returned as a structured dictionary:
```text
{
    'monitor_id': 1,
    'health_status': 'UP',
    'expected_status': 200,
    'http_status': 200,
    'latency_ms': 225.33,
    'reason': '-',
    'checked_at': ...
}
```
Different examples in main.py demonstrate:

- Successful requests;
- Expected error responses;
- Unexpected `2xx` responses;
- Unexpected `4xx` responses;
- Unexpected `5xx` responses;
- Request timeouts.
